# 近 7 天總結 — 設計文件

日期：2026-08-09
狀態：已實作（2026-08-09）

## 目標

讓用戶用一則指令看到近 7 天的飲食全貌，重點是**累積熱量赤字** —— 單日進度看不出趨勢，而減脂成效取決於一段時間的累積差額。

## 範圍

**做：** 用戶主動查詢的靜態卡片。
**不做（本版）：** 主動推播、AI 講評、體重趨勢、常吃店家、赤字換算體重。

### 為什麼不做推播

Reply API 免費不計額度，Push API 計入 LINE 免費方案每月 200 則。一人一週一則 = 每月 4 則，50 個用戶就用光整個額度。而且 Render 免費方案沒有排程器，得外掛 cron 服務。

先做查詢版驗證「有沒有人看」，確定有價值再談推播。

### 為什麼不做 AI 講評

數字是確定性的，程式算完就對。加 AI 要多一次呼叫（依實測，推薦那條路的模型時間是 3~7 秒），而且模型算錯數字是這個專案已經踩過的坑（份量修正那次把 1038 kcal 的餐算成 565）。

之後若要加，做法是把算好的數字塞給模型照抄 —— 提示裡已有「必須完全照抄給定的正確數字」這條先例。

## 進入點

- 文字指令：`本週總結`、`週報`、`這週如何`
- `get_quick_reply` 增加一顆「本週總結」按鈕（目前 5 顆，LINE 上限 13）

指令比對放在既有指令區（`個人檔案` / `體重紀錄` 那一段），在所有 AI 路徑之前。

## 「近 7 天」的定義

**滾動 7 天**，含今天，即 `today - 6` 到 `today`。

不用「週一至今」的原因：週一早上查只有一天資料，卡片會是空的。代價是標題必須寫「近 7 天」而不是「本週」。

## 資料來源

不需要改 schema。三次查詢，與 `get_quick_reply` 同一個模式：

| 查詢 | 用途 |
|---|---|
| `daily_logs` where `user_id` and `log_date >= today-6` | 取得該區間的 log id 與日期 |
| `meal_items` where `daily_log_id in (...)` | 每日熱量與蛋白質加總 |
| `profiles`（呼叫端已持有）| `target_calories`、`target_protein_g`、`goal` |

`weight_logs` 不查（本版不顯示體重）。

## 計算規則

### 只計算「有記錄的天數」

這是本設計最重要的一條。

若 7 天中只記了 5 天，用 7 天算應攝取會得到灌水的赤字：那兩天用戶有吃，只是沒記。**一個假的赤字比沒有赤字更糟** —— 它會讓減脂的人以為自己瘦了。

所以：

```
logged_days = 該區間內「有至少一筆 meal_items」的天數
should_intake = logged_days × target_calories
actual_intake = 該區間所有 meal_items 的 calories 總和
diff = actual_intake - should_intake      # 負數 = 赤字
```

達標天數的分母同樣是 `logged_days`，不是 7。

### 達標的定義

單日 `calories <= target_calories` 即為達標。

（曾考慮「落在目標 80%~100%」以避免把「只吃 800 卡」算成達標，但這會讓正常的輕食日被判為未達標，誤傷較大。本版採用簡單定義。）

### 逐日直條圖

重用體重趨勢卡的手法（`filler` + `flex` 比例撐高度），不需要新技術。

柱高以區間內最高的單日熱量為基準做比例。顏色編碼狀態：

| 顏色 | 意義 |
|---|---|
| `#27AE60` 綠 | 當日在目標內 |
| `#EF4444` 紅 | 當日超標 |
| `#9CA3AF` 灰 | 當日沒有記錄（給最低高度，避免被誤讀成「那天吃 0 卡」）|

### 進度條

直接呼叫既有的 `_progress_bar_block("累積攝取", actual_intake, should_intake, "kcal", bar_color, over_color)`。

顏色依目標調換 —— 對增肌的人，「沒吃到」才是問題：

| goal | bar_color | over_color |
|---|---|---|
| `fat_loss` / `recomp` | `#27AE60` 綠 | `#EF4444` 紅 |
| `muscle_gain` | `#3B82F6` 藍 | `#27AE60` 綠 |

### 累積赤字／盈餘

`diff < 0` 顯示「累積赤字 −X kcal」，`diff > 0` 顯示「累積盈餘 +X kcal」，`diff == 0` 顯示「持平」。

文字顏色同樣依目標判斷是否為好消息（減脂：赤字綠、盈餘紅；增肌相反）。

## 邊界情況

| 情況 | 行為 |
|---|---|
| `logged_days == 0` | 回文字：「近 7 天還沒有任何記錄。」不畫卡片 |
| `1 <= logged_days < 3` | 不畫圖表，回文字說明資料不足以看出趨勢，鼓勵再記幾天 |
| 某日有 `daily_logs` 但沒有 `meal_items` | 視為沒記錄（灰柱、不計入 logged_days）|
| 所有日熱量皆為 0 | 柱高全部給最低值，不做除以零 |
| `target_calories` 為 None | 沿用既有 fallback `2000` |

## 附帶修正

`app.py:340` 的 `_progress_bar_block`：

```python
pct = min(100, max(0, int((current / target) * 100)))
```

百分比被夾在 100 —— **超標時文字顯示「(100%)」而不是真實的 116%**。今日卡片現在就有這個問題。

修法：條寬仍夾在 100（不然會爆版），但顯示用的百分比不夾。兩張卡片同時受益。

## 驗收

1. 有 6 天記錄時：卡片顯示 6 根彩色柱 + 1 根灰柱，分母為 6，赤字＝6 天應攝取減實際
2. 有 0 天記錄：回文字，不畫卡片
3. 有 2 天記錄：回文字說明資料不足
4. 單日超標：該柱為紅，且進度條文字顯示真實百分比（非 100%）
5. `goal = muscle_gain`：進度條顏色為藍→綠，赤字標紅
6. 所有 Flex `text` 非空（沿用 `sanitize_flex` 兜底）

前四項可用假資料在測試腳本中驗證，不需連線資料庫。
